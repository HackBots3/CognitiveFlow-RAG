    S2 - Install Ollama Natively on Windows (NOT in Docker) : On Host
        -> Problem With : Docker-Ollama on Windows (Every Layer Adds Latency)
                Docker Desktop on Windows = WSL2 VM running Linux = container inside that Linux VM. For an Ollama container to access your NVIDIA GPU, the call path is
                    App code (in container)
                        → container runtime (in WSL2)
                            → WSL2 VM (with GPU passthrough)
                                → Windows NVIDIA driver
                                    → RTX 3050 GPU

        -> Solution With : host-native Ollama (One network hop vs. multi-layer virtualization. 5–7× speedup)
                Ollama as a regular Windows app has direct GPU access via the Windows NVIDIA driver. The call path is:
                    Docker container (your FastAPI backend)
                        → host.docker.internal (crosses the WSL2/network boundary once)
                            → Ollama on Windows host
                                → Windows NVIDIA driver
                                    → RTX 3050 GPU

        -> Configure OLLAMA_HOST=0.0.0.0:11434 (not the default 127.0.0.1)
                127.0.0.1 (localhost) — only accepts connections from processes on the same machine (same network namespace)
                0.0.0.0 — accepts connections from any IP, including Docker's virtual network

        -> Setup Steps:
            1. Install Ollama for Windows
            2. Run "OllamaSetup.exe" and Install 
            3. Set env variable : [Variable name: OLLAMA_HOST , Variable value: 0.0.0.0:11434]
            4. Relaunch and verify(model running) : curl http://localhost:11434/api/tags -> returns  {"models":[]}

        ** "In production, LLM inference runs on dedicated compute clusters — vLLM on Kubernetes, Triton Inference Server, or managed endpoints — 
            decoupled from the application and ingestion layer. We mirrored that decoupling: state, search, and background workers in Docker, 
            while serving the model from a separate endpoint with direct GPU passthrough. Same architectural pattern, just on a dev-laptop scale."


    S3 - Pulling Three Ollama Models using script (scripts/pull_models.sh)
        ->  qwen2.5:3b-instruct (Primary LLM):
                3 billion parameters at Q4 quantization =around= 2.2GB
                "Instruct" tuned - follows instructions well for routing and grading tasks
                "Small fast model for routing/grading, large slow model for final answer" — same pattern GPT-4 + GPT-3.5 used in early ChatGPT

        ->  llama3.1:8b (Heavy reasoning):
                8B parameters, Q4 quantized = 4.7GB
                Used only for: final user-facing answer generation in Phase 4, eval suite in Phase 7
                this model included for hard question to deliver quality not speed
        
        ->  bge-m3 (Embeddings):
                BAAI's multilingual embedding model — works for English, Chinese, 100+ languages
                Produces 1024-dim dense vectors - semantic balance small enough for speed, big enough for nuance
                Also produces sparse vectors (BM25-style) in the same call — rare feature
                Hybrid (dense + sparse) = best of both worlds: semantic understanding + exact keyword matc

        ->  Setup steps:
                1. Pull directly using the ollama CLI in PowerShell (one by one) || 
                2. Run the script (PowerShell) : bash scripts/pull_models.sh  || one by one "ollama pull ..."

    S4 - Save docker-compose.yml ((5 services, ~1.2GB idle RAM) plus .env.example)
        -> Services:
            -postgres:16-alpine:
                Alpine variant = 80MB image vs 400MB+ standard — saves disk and RAM
                Postgres 16 = latest stable, JSONB improvements, better query performance
                Stores: documents metadata, chunks (with full text), queries history, eval results
                Volume postgres_data = data survives across container restarts
                Healthcheck pg_isready = backend waits for Postgres to be ready before starting

            -redis:redis-stack-server:7.4.0-v0:
                "stack-server" = includes RediSearch module (we need it for semantic cache in Phase 5)
                "server-only" (no UI) = saves ~100MB RAM vs full redis-stack with RedisInsight UI
                Two roles: (1) Celery broker (task queue), (2) future semantic cache for chat
                Volume redis_data = task results persist across restarts

            -qdrant/qdrant:v1.10.0:
                v1.10 has stable native hybrid vector support (dense + sparse in one collection)
                Two ports: 6333 (HTTP API + dashboard) + 6334 (gRPC — faster for bulk upserts)
                Why Qdrant over Pinecone/Weaviate? Open-source, runs locally, native hybrid search
                Volume qdrant_data = vectors survive across restarts
                
            -backend (FastAPI) - we'll wire this in Day 2:
                Builds from ../backend/Dockerfile:
                extra_hosts: host.docker.internal:host-gateway = lets backend reach Ollama on host
                Env vars pass through: DATABASE_URL, REDIS_URL, QDRANT_URL, OLLAMA_URL, etc.
                Volume mounts source code so hot-reload works (edit code → uvicorn reloads instantly)
                --reload flag = dev mode, picks up changes without rebuild

            -celery_worker - we'll wire this in Day 3:
                Same Dockerfile as backend (uses same code)
                Different command: celery -A app.workers.celery_app worker
                concurrency=2 = handle 2 tasks in parallel (matches our 4GB VRAM budget — each embedding job needs RAM)
                Why same image? Celery imports from app code — no need for a separate Dockerfile

        -> Setup steps:
                1.  docker compose up -d postgres redis qdrant (Boots 3 reqiured datastores first)
                2. Then Use up via [docker compose up/down]
