    S2 - Install Ollama Natively on Windows (NOT in Docker) : On Host
        -> Problem With : Docker-Ollama on Windows (Every Layer Adds Latency)
                Docker Desktop on Windows = WSL2 VM running Linux = container inside that Linux VM. For an Ollama container to access your NVIDIA GPU, the call path is
                    App code (in container)
                        → container runtime (in WSL2)
                            → WSL2 VM (with GPU passthrough)
                                → Windows NVIDIA driver
                                    → RTX 3050 GPU

        -> Solution With : host-native Ollama (One network hop vs. multi-layer virtualization. 5–7× speedup)
                Ollama as a regular Windows app has direct GPU access via the Windows NVIDIA driver. The call path is:
                    Docker container (your FastAPI backend)
                        → host.docker.internal (crosses the WSL2/network boundary once)
                            → Ollama on Windows host
                                → Windows NVIDIA driver
                                    → RTX 3050 GPU

        -> Configure OLLAMA_HOST=0.0.0.0:11434 (not the default 127.0.0.1)
                127.0.0.1 (localhost) — only accepts connections from processes on the same machine (same network namespace)
                0.0.0.0 — accepts connections from any IP, including Docker's virtual network

        -> Setup Steps:
            1. Install Ollama for Windows
            2. Run "OllamaSetup.exe" and Install 
            3. Set env variable : [Variable name: OLLAMA_HOST , Variable value: 0.0.0.0:11434]
            4. Relaunch and verify(model running) : curl http://localhost:11434/api/tags -> returns  {"models":[]}

        ** "In production, LLM inference runs on dedicated compute clusters — vLLM on Kubernetes, Triton Inference Server, or managed endpoints — 
            decoupled from the application and ingestion layer. We mirrored that decoupling: state, search, and background workers in Docker, 
            while serving the model from a separate endpoint with direct GPU passthrough. Same architectural pattern, just on a dev-laptop scale."

    S3 - "backend/app/config.py" - A Pydantic Settings class that:
            Reads all env vars (Postgres URL, Redis URL, Ollama URL, etc.) -> lead with defaults
            Provides sensible defaults
            Exposes a singleton settings instance imported across the app

        -> The problem with os.getenv:
            # Bad pattern — scattered across codebase
            database_url = os.getenv("DATABASE_URL")
            if not database_url:
                raise RuntimeError("DATABASE_URL not set")
            # No type validation, no defaults, no .env file loading, error at runtime not startup

        -> Pydantic Settings solves all of this:
            # Good — one place, type-validated, .env-aware
            class Settings(BaseSettings):
                database_url: str        # Required, fails at startup if missing
                ollama_url: str = "http://host.docker.internal:11434"  # Default value

        -> WHY SettingsConfigDict(env_file=".env", extra="ignore")
            env_file=".env" — automatically reads .env file if present (local dev convenience)
            extra="ignore" — if env vars exist that aren't in our Settings class, don't error (Docker passes many vars we don't care about)
            Without extra="ignore", an unknown env var like PATH=/usr/bin would cause validation errors

        -> WHY a module-level settings = Settings() instance
            Singleton pattern — instance created once at module import
            All other modules import: from app.config import settings
            Reads env vars exactly once at startup (fail-fast)
            No need to pass settings through function arguments everywhere

Day 3: Qdrant collection created (hybrid schema with dense + sparse vectors), Celery worker executes ping task, all 7 pytest smoke tests green.
    S1 - "scripts/seed_qdrant.sh"
        A bash script that calls Qdrant's REST API to create the docs collection with hybrid schema — meaning it stores BOTH:
            Dense vectors (1024-dim Cosine) — semantic similarity
            Sparse vectors (BM25-style indices) — exact keyword match

        Hybrid = both: dense catches semantic meaning, sparse catches exact keywords, you fuse the rankings.
        
        -> WHY specific schema choices
            {
              "vectors": {
                "dense": {"size": 1024, "distance": "Cosine"}
              },
              "sparse_vectors": {
                "sparse": {}
              }
            }
            size: 1024 — matches bge-m3 embedding dimension. Mismatch = upsert fails.
            distance: "Cosine" — for semantic similarity, cosine is the standard. L2 (Euclidean) overweights vector magnitude. Dot product requires normalized vectors.
            sparse: {} — empty config = use Qdrant's default sparse config. We'll provide the sparse vectors ourselves (from bge-m3's sparse output).

        -> WHY this is a one-time script (not a migration)
            Qdrant is schema-as-code — collections live in storage, not source control
            Running it twice with PUT is idempotent — overwrites the collection (warning: deletes points)
            This is "infrastructure as code" for vectors — same pattern as CREATE TABLE SQL scripts

        -> Save and Run the Script:
            bash scripts/seed_qdrant.sh
           Verify:
            Verify in Qdrant dashboard: Browser → http://localhost:6333/dashboard → should see docs collection listed

    S2 - "backend/app/workers/celery_app.py" (fixes the crashing Celery container)
        A Python module that:
            Creates a Celery instance with Redis as both broker (task queue) and backend (result store)
            Configures task serialization, timezone, routing
            Defines a ping task that returns "pong"
    
        -> Why each config setting:
            task_track_started=True — Without this, a task goes PENDING → SUCCESS/FAILURE, skipping STARTED. With it, you can see "task X is currently running" in monitoring.
            
            task_serializer="json" — Default is pickle (Python-only, security risk). JSON is cross-language and safe. Trade-off: can't serialize complex Python objects, but our tasks only use dicts/lists/strings.

            accept_content=["json"] — Only accept JSON-serialized tasks. Older workers accepting pickle = security hole (deserialization RCE). Lock down early.

            timezone="UTC" — All timestamps in UTC. Avoids "task scheduled at 9 AM EST ran at 2 PM UTC" bugs.

            task_routes — Sends app.ingestion.tasks.* to a dedicated ingestion queue. Lets you scale ingestion workers separately from other workers. Phase 2 will add the actual ingestion task here.

        -> WHY Redis as both broker AND backend
            Broker: Where tasks get enqueued (the queue)
            Backend: Where results get stored after task completes

        -> Using Redis for both is fine for dev (one less service). In production:
            Broker: Redis or RabbitMQ (RabbitMQ is more robust for high-volume)
            Backend: Postgres or dedicated result store (Redis is fine for short-lived results)

        -> WHY a ping task
            Simplest possible task — no DB calls, no LLM calls, just returns a string
            Tests the full Celery wiring: broker → worker → backend → result retrieval
            If ping works, you know Redis is reachable, worker is alive, serialization works, result backend works
            Same pattern as /health endpoint — fail loudly, fail specifically

        -> Save the file at backend/app/workers/celery_app.py

    S5 - "backend/tests/test_smoke_celery.py" (1 test, but the most important)
        A single end-to-end test that proves the entire Celery wiring:
            Test enqueues ping.delay() → task pushed to Redis broker
            Celery worker (running in Docker) picks up task
            Worker executes ping() → returns "pong"
            Worker stores result in Redis backend
            Test calls result.get(timeout=10) → retrieves "pong"
            Assert: val == "pong"

        -> WHY this is the most important test
            This single test proves 6 things simultaneously:
                ✅ Redis is reachable (broker)
                ✅ Redis is reachable (backend)
                ✅ Celery worker is running
                ✅ Worker can deserialize JSON tasks
                ✅ Worker can serialize JSON results
                ✅ Result backend polling works
            If any one of these breaks, this test fails. That's the value — one test, six guarantees.

        -> WHY time.sleep(2) before result.get()
            result = ping.delay()
            time.sleep(2)  # let worker pick up and execute
            val = result.get(timeout=10)
            ping.delay() returns immediately with an AsyncResult (task is queued, not done)
            result.get(timeout=10) blocks up to 10s for the result to appear in backend
            The time.sleep(2) is defensive — gives worker a head start
            Without it: get(timeout=10) would still work (polls Redis every ~250ms), just slightly slower on success path
            With it: less polling, less Redis load

        -> WHY timeout=10
            ping task takes ~50ms to execute
            10s timeout = 200× headroom
            If it takes longer, something is wrong (worker crash, Redis lock, etc.)
            Don't set timeout=None (would block forever on a hung worker)

        -> WHY a singleton client (not per-request)
            Langfuse client opens HTTP connections + buffers spans in memory
            Creating one per request = connection thrashing
            Singleton = reused across requests, flushed in batches
            Same pattern as our pg_engine, redis_client, qdrant_client

        -> WHY trace() is a context manager (not a decorator)
            Decorator pattern (limitation):
                @trace("health-check")
                async def health():
                    ...
                # Can't easily attach metadata mid-function
        
            Context manager pattern (flexible):
                async def health():
                    with trace("health-check") as span:
                        if span:
                            span.metadata = {"endpoint": "/health"}
                            span.input = {"user": "test"}
                        # ... existing logic ...
                        if span:
                            span.output = checks

            Can attach input/output/metadata at any point inside the function
            Can nest: with trace("request"): → with trace("db-call"): inside
            More Pythonic — matches with open(...) pattern

        -> WHY no-op fallback when Langfuse not configured
            if lf is None:
                yield None
                return

            If LANGFUSE_HOST is empty (e.g., running tests), trace() is a no-op
            Code still works — just no spans emitted
            Critical for tests: smoke tests don't need to hit Langfuse
            Critical for local dev: developer can disable Langfuse by clearing env var

        -> WHY try/except around lf.span()
            try:
                with lf.span(name=name) as span:
                    yield span
                except Exception as e:
                logger.warning(f"Langfuse span '{name}' failed: {e}")
                yield None

            Network failures (Langfuse Cloud unreachable) shouldn't break /health
            Tracing is observability — it should NEVER cause user-facing failures
            This is the golden rule of observability: tracing must be best-effort
